# 后台交易体系管理与规则库 UI 优化开发提示词

## 开发任务

优化后台管理中的交易体系管理与规则库管理 UI。

当前后台管理中，“交易体系管理”和“规则定义列表”混在同一个页面，用户理解成本较高。本次任务目标是把二者职责拆开，让用户可以清晰维护多套交易体系，并能按生命周期绑定和配置规则。

本次重点是后台管理 UI 和交互结构优化，不是重写后端核心模型。

## 背景理解

系统目前已经具备以下能力：

- 交易体系定义
- 规则定义
- 交易体系与规则绑定
- 规则执行器
- 规则参数配置
- 自选观察 / 信号 / 交易流程
- 后台任务与规则监控

交易体系与规则的关系应理解为：

- 交易体系：平台突破、上涨趋势、涨停接力、超跌反弹等完整交易方法。
- 规则库：15分钟低背离、跌破MA5、收破平台支撑位、5分钟顶背离等可复用规则。
- 体系规则绑定：某个交易体系在某个生命周期阶段启用哪些规则，以及规则参数如何配置。

## 总体要求

请基于当前项目代码实现，不要大规模重构后端模型。

优先复用已有接口、组件和数据结构。

实现后需要满足：

- 后台菜单结构更清晰。
- 交易体系管理和规则库管理分开。
- 交易体系详情能按生命周期展示规则。
- 规则绑定编辑更清晰。
- 支持规则配置参数编辑。
- 支持基础的配置完整性提示。
- 不影响 H5 前端已有自选观察 / 信号 / 交易功能。
- 不影响现有后台任务管理功能。

## 第一步：梳理现有代码

请先阅读并理解以下代码，不要急于修改：

- 后台页面入口
- 后台交易体系管理页面
- 交易体系相关 API
- 规则定义相关 API
- 规则绑定相关 API
- 规则执行器注册逻辑
- 自选观察 / 信号 / 交易页面如何使用交易体系与规则结果

重点检查：

1. 当前后台 Admin 页面有哪些菜单项。
2. 当前交易体系管理页面如何展示系统、规则、绑定关系。
3. 当前是否已经有以下接口：
   - 查询交易体系列表
   - 新增 / 编辑交易体系
   - 查询规则定义列表
   - 新增 / 编辑规则定义
   - 查询交易体系参数
   - 查询交易体系绑定规则
   - 新增 / 编辑 / 删除规则绑定
   - 查询规则执行器列表
4. 当前规则绑定是否支持 `config_json`。
5. 当前前端是否支持编辑 `config_json`。
6. 当前规则类型枚举是否包含：
   - `buy_signal`
   - `sell_signal`
   - `stop_loss`
   - `filter`
   - `confirm`
   - `observe_risk`
   - `invalid_signal`
   - `remove_signal`

完成后，请先输出你的理解和准备修改的文件清单，再开始修改。

## 第二步：拆分后台菜单

将后台管理中的交易体系相关功能拆分成至少两个清晰菜单：

1. `交易体系`
2. `规则库`

如果现有后台菜单结构允许，也可以增加：

3. `执行器`
4. `规则试算`

本次不要过度开发。优先保证前两个菜单清晰可用。

### 交易体系菜单

用于维护完整交易体系。

例如：

- 平台突破
- 上涨趋势
- 涨停接力
- 超跌反弹

### 规则库菜单

用于维护全局可复用规则。

例如：

- 15分钟低背离
- 跌破MA5
- 收破平台支撑位
- 5分钟顶背离

注意：

- 规则库页面不应该混入某个交易体系的绑定配置。
- 交易体系页面可以引用规则库中的规则。

## 第三步：实现交易体系管理页面

交易体系管理页面建议采用：

```text
左侧：交易体系列表
右侧：交易体系详情
```

右侧详情区使用 Tab 或分区展示：

1. 概览
2. 参数定义
3. 观察阶段
4. 买点确认阶段
5. 交易中阶段
6. 卖点阶段
7. 止损阶段
8. 风险 / 失效 / 自动剔除

如果当前 UI 组件不适合 Tab，也可以使用分组卡片，但必须保持结构清晰。

### 概览区域

展示：

- 交易体系名称
- 交易体系编码
- 描述
- 是否启用
- 当前绑定规则数量
- 各阶段规则数量
- 最近更新时间

支持编辑：

- 名称
- 描述
- 是否启用

### 参数定义区域

展示当前交易体系参数。

例如平台突破可能包含：

- 平台上沿价格
- 平台支撑位
- 剔除价位
- 止损价位
- 观察周期
- 目标周期

支持：

- 新增参数
- 编辑参数
- 删除参数
- 设置参数类型
- 设置是否必填
- 设置默认值
- 设置说明

### 生命周期规则区域

按阶段展示已绑定规则。

阶段建议映射：

```text
observe      -> 观察阶段
buy_confirm -> 买点确认阶段
trading     -> 交易中阶段
sell        -> 卖点阶段
stop_loss   -> 止损阶段
```

风险、失效和自动剔除建议按规则类型展示在独立区域：

```text
observe_risk   -> 观察风险
invalid_signal -> 观察失效
remove_signal  -> 自动剔除
```

如果后端已有不同 stage 字段，请优先兼容现有字段，不要强行破坏旧数据。

每个阶段下展示：

- 规则名称
- 规则编码
- 规则类型
- 执行器
- 周期级别
- 是否启用
- 排序
- 配置摘要
- 操作按钮：编辑、启用 / 停用、删除

支持在某个阶段下添加规则绑定。

添加绑定时：

- 从规则库选择规则
- 设置阶段
- 设置排序
- 设置是否启用
- 设置绑定配置参数

## 第四步：实现规则库管理页面

规则库页面用于维护全局规则定义。

列表字段建议：

- 规则名称
- 规则编码
- 规则类型
- 执行器 key
- 周期级别
- 描述
- 是否启用
- 被多少个交易体系使用
- 更新时间
- 操作

支持筛选：

- 关键字
- 规则类型
- 执行器
- 周期级别
- 启用状态

支持操作：

- 新增规则
- 编辑规则
- 启用 / 停用规则
- 查看被哪些交易体系引用

规则类型必须补齐以下选项：

```text
buy_signal
sell_signal
stop_loss
filter
confirm
observe_risk
invalid_signal
remove_signal
```

中文显示建议：

```text
buy_signal     -> 买点信号
sell_signal    -> 卖点信号
stop_loss      -> 止损信号
filter         -> 过滤条件
confirm        -> 确认条件
observe_risk   -> 观察风险
invalid_signal -> 观察失效
remove_signal  -> 自动剔除
```

## 第五步：优化规则绑定配置编辑

当前如果规则绑定支持 `config_json`，前端必须提供编辑入口。

要求：

1. 不要只隐藏在后端。
2. 不要让用户完全无法修改规则参数。
3. 常见规则尽量结构化编辑。
4. 暂时无法结构化的规则，允许高级 JSON 编辑。

### 推荐实现方式

新增一个规则配置编辑组件，例如：

```text
RuleConfigEditor
```

输入：

- `executor_key`
- 当前 `config_json`
- 当前 `rule_type`
- 当前 `timeframe`

输出：

- 修改后的 `config_json`

### 常见执行器结构化配置

至少支持以下执行器的基础配置展示与编辑。

#### break_level

字段建议：

- 价格来源：
  - 固定值
  - 观察参数
  - 平台上沿
  - 平台支撑位
  - 剔除价位
- 价格字段 / 参数名
- 触发方式：
  - 盘中跌破
  - 收盘跌破
  - 收盘收破
- 容差比例
- K线级别

#### break_ma

字段建议：

- 均线：
  - MA5
  - MA10
  - MA20
  - MA30
- 触发方式：
  - 盘中跌破
  - 收盘跌破
- K线级别

#### pullback_to_level

字段建议：

- 参考价格来源
- 回撤比例
- 接近容差
- K线级别

如果当前系统还有其他执行器，例如 MACD、背离、金叉死叉等，请尽量兼容已有配置。

### 高级 JSON

每个规则配置编辑器底部保留：

```text
高级配置 JSON
```

要求：

- JSON 格式错误时不能保存。
- 错误提示清楚。
- 不要破坏已有配置字段。

## 第六步：增加配置完整性提示

在交易体系详情页增加基础检查提示。

至少检查：

1. 已启用绑定是否缺少规则。
2. 已启用绑定是否缺少执行器。
3. 已启用绑定的执行器是否存在于执行器注册列表中。
4. 规则需要的参数是否在交易体系参数中存在。
5. 规则需要的 K线周期是否明显缺失配置。
6. `config_json` 是否不是合法 JSON。
7. 规则类型是否无法识别。

展示方式：

- 页面顶部显示一个轻量提示区。
- 每条绑定旁边显示小提示。
- 不要阻塞所有保存，除非 JSON 格式非法。

提示文案要面向普通用户，例如：

```text
规则“跌破平台支撑位”需要参数 platform_support_price，但当前交易体系未定义该参数。
```

## 第七步：保证 H5 前端不受影响

本次重点修改后台管理页面。

请确保：

1. 不修改 H5 自选观察 / 信号 / 交易的核心数据结构。
2. 不破坏已有接口返回字段。
3. 不改变已有规则执行结果格式。
4. 不改变观察股、信号、交易的状态流转。
5. 不影响后台任务运行。

如果必须调整接口字段，请做到向后兼容。

## 第八步：UI 体验要求

后台管理是配置型页面，不要做营销风格页面。

要求：

- 信息密度适中。
- 表格、列表、分组清晰。
- 操作按钮位置稳定。
- 不要把多个大表单堆在同一屏。
- 不要把规则库和体系绑定混在一起。
- 重要状态用标签显示。
- 危险操作需要确认。
- 编辑区要有保存 / 取消。
- 页面刷新后数据仍然正确。

建议视觉风格：

- 延续当前后台页面风格。
- 使用清晰的左右布局。
- 用 Tab 或阶段分组表达生命周期。
- 操作按钮不要过多抢眼。
- 保持和现有“我的 / 后台任务管理”等页面风格一致。

## 第九步：验证要求

实现完成后，请执行以下检查。

### 代码检查

- 前端 TypeScript 无明显类型错误。
- 构建通过。
- 不引入未使用的大型依赖。
- 不产生无关格式化修改。

### 功能检查

请至少手动验证以下流程：

1. 进入后台管理。
2. 能看到独立的“交易体系”菜单。

9. 能编辑绑定规则的配置。
10. 能启用 / 停用绑定规则。
11. 进入“规则库”。
12. 能新增 / 编辑规则。
13. 能选择 `observe_risk`、`invalid_signal`、`remove_signal`。
14. JSON 配置错误时不能保存。
15. 保存后刷新页面数据仍然存在。
16. H5 自选观察 / 信号 / 交易页面仍然能正常打开。

### 回归检查

确认以下功能未被破坏：

- 自选观察列表
- 自选信号列表
- 自选交易列表
- 后台任务管理
- 自选监控任务
- 自动剔除任务

- K线数据更新任务

## 注意事项

请不要做以下事情：

1. 不要重写整个后台管理系统。
2. 不要重构 H5 自选页面。
3. 不要改变观察 / 信号 / 交易核心状态机。
4. 不要删除已有交易体系或规则数据。
5. 不要强制要求用户手写所有 JSON。
6. 不要引入复杂权限系统。
7. 不要引入审计日志。
8. 不要做无关 UI 美化。
9. 不要引入新的大型前端框架。
10. 不要破坏现有 API 兼容性。

本次目标是：

> 让后台交易体系管理和规则库管理职责分离，让用户能清晰地配置多套交易体系，并能按生命周期管理规则绑定。
